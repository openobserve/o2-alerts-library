# OpenObserve Alert Library

Production-ready alert rules for [OpenObserve](https://openobserve.ai) — 1,200+
of them across 15 packs, covering Kubernetes, databases, message brokers,
proxies, runtimes, cloud providers and the observability stack itself. Each is
a ready-to-import alert definition with a title, a severity and the PromQL or
SQL it evaluates; `manifest.json` indexes the lot.

---

## What is OpenObserve?

[OpenObserve](https://openobserve.ai) is an open-source, cloud-native observability platform designed for **logs, metrics, and traces at petabyte scale**. It is a unified, self-hostable alternative to the Elasticsearch + Grafana + Prometheus stack — simpler to operate and up to **140× cheaper in storage costs**.

### Core Capabilities

| Capability | Description |
|-----------|-------------|
| **Logs** | Ingest, search, and alert on structured and unstructured log data |
| **Metrics** | Prometheus-compatible metric storage with full PromQL support |
| **Traces** | Distributed tracing via OpenTelemetry |
| **Dashboards** | Built-in visualization — no separate Grafana needed |
| **Alerts** | Rule-based alerting with Slack, PagerDuty, email, and webhook support |
| **SQL Search** | Query any stream (logs or metrics) using familiar SQL syntax |

OpenObserve ingests data via the **OpenTelemetry Collector** and exposes a Prometheus-compatible API, meaning existing PromQL queries and OTel instrumentation work without modification.

## How Alerting Works in OpenObserve

Alerts in OpenObserve are **scheduled rules** that periodically evaluate a query and send notifications when conditions are met. Two query types are supported.

### PromQL Alerts (Metrics)

Best for continuous numeric metrics — CPU, memory, latency, error rates.

```
Evaluation flow:
  stream_name  →  PromQL expression  →  promql_condition  →  trigger_condition  →  notification
```

Key alert parameters:

| Parameter | Purpose |
|-----------|---------|
| `stream_name` | The metric stream to query |
| `promql` | PromQL expression to evaluate |
| `promql_condition` | Threshold filter on the result (e.g. `>= 80`) |
| `trigger_condition.period` | Look-back window in minutes |
| `trigger_condition.frequency` | How often to evaluate (minutes) |
| `trigger_condition.threshold` | Min number of matching series needed to fire |
| `trigger_condition.silence` | Cooldown period after firing (minutes) |
| `row_template` | Per-series format string in the notification |
| `destinations` | Slack / webhook / email endpoints to notify |

### SQL Alerts (Logs & Metrics)

Best for event-driven detection — log pattern matching, Kubernetes events, complex aggregations.

```sql
SELECT count(*) as event_count, cluster, namespace
FROM "my_log_stream"
WHERE str_match(level, 'ERROR')
GROUP BY cluster, namespace
HAVING event_count > 10
```

Key SQL functions:

| Function | Use |
|----------|-----|
| `str_match(field, 'value')` | Contains-style filter on a specific field |
| `match_all('value')` | Full-text search across all fields |
| `AVG(value)` | Average a gauge metric over the query window |
| `MAX(value) - MIN(value)` | Approximate `increase()` for counter metrics |

### Notifications

Each destination uses a **template** to format the notification body. The `{rows}` placeholder expands the per-alert `row_template` for each firing series.

```
🚨 *Alert:* high_cpu_utilization
*ClusterName:* production | Node: web-01 | CPU: 91.43%
*ClusterName:* staging | Node: web-02 | CPU: 83.12%
```

## Repository Structure

Every alert lives at exactly one depth — `packs/<pack>/alerts/<category>/<name>.json` —
and `manifest.json` at the repository root is the machine index of all of them.

```
o2-alerts-library/
│
├── README.md                        ← You are here
├── LICENSE                          ← CC BY 4.0
├── ATTRIBUTION.md                   ← Licences of the imported rule sets
├── manifest.json                    ← CI-generated index — never hand-edited
├── PACKS.md                         ← CI-generated pack/category listing
│
├── packs/
│   ├── k8s/
│   │   ├── alerts/<category>/*.json
│   │   ├── tests/                   ← kubectl manifests to trigger each alert
│   │   └── README.md
│   ├── databases/alerts/<category>/*.json
│   └── …                            ← one directory per pack
│
└── scripts/
    ├── generate_manifest.py         ← builds manifest.json + PACKS.md (CI only)
    ├── validate_alerts.py           ← the contract every alert file must meet
    └── import_awesome_prometheus_alerts.py
```

`manifest.json` is generated by CI on every merge to `main` and committed by a
bot; nobody edits it by hand. It carries one entry per alert — id, pack,
category, title, severity, description, stream, path and a content hash — so a
UI renders the whole gallery from a single request and fetches an individual
alert file only when it is opened or installed.

The repository is mirrored byte-for-byte to
`s3://openobserve-datasources-bucket/alerts/`, so the paths above are also the
public URLs.

## Packs

**[`PACKS.md`](./PACKS.md) lists every pack and category with current
counts** — it is generated by CI from the tree, so it cannot drift.

Thirteen packs — everything except `k8s` and `openobserve` — are imported from
[awesome-prometheus-alerts](https://github.com/samber/awesome-prometheus-alerts)
(CC BY 4.0). They are generated wholesale by
`scripts/import_awesome_prometheus_alerts.py` and must not be hand-edited; see
[`ATTRIBUTION.md`](./ATTRIBUTION.md).

### A note on the imported PromQL

A Prometheus rule bakes its threshold into the expression (`node_load1 > 5`),
while OpenObserve evaluates `({promql}) {operator} {value}` and needs the two
apart. The importer therefore splits every query. Where the outermost operator
is `and`/`or`/`unless`, or the comparison is against another series, splitting
would change the parse — those queries are instead normalised to
`(<query>) * 0 + 1` with a `>= 1` condition, which fires on exactly the series
the upstream rule would have matched but reports a constant `1` as the observed
value. Those alerts say so in `source.query_normalized`, and every alert keeps
the untouched original in `source.upstream_query`.

## Setup: Alert Templates and Destinations

Before any alert can send notifications, you need two things configured in OpenObserve: a **template** (how the message is formatted) and a **destination** (where to send it). This applies to all domains in this library.

### Step 1 — Create an Alert Template

A template defines the notification body. It supports `{alert_name}` and `{rows}` placeholders — `{rows}` expands the per-alert `row_template` for each firing series.

**In the OpenObserve UI:**
1. Go to **⚙️ Management → Templates → New Template**
2. Name it (e.g. `k8s_alert_template`)
3. Set type to `HTTP`
4. Paste the body:

```json
{
  "text": "🚨 *Alert:* {alert_name}\n{rows}"
}
```

**Via API:**
```bash
curl -X POST \
  "https://<your-openobserve>/api/default/alerts/templates" \
  -H "Authorization: Basic <base64(user:password)>" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "k8s_alert_template",
    "type": "http",
    "body": "{\"text\": \"🚨 *Alert:* {alert_name}\\n{rows}\"}"
  }'
```

**Available template variables:**

| Variable | Value |
|----------|-------|
| `{alert_name}` | Name of the alert rule |
| `{rows}` | All matching series, each formatted by the alert's `row_template` |
| `{org_name}` | Organization name |
| `{stream_name}` | Stream being queried |
| `{alert_type}` | `scheduled` or `realtime` |

The `row_template` on each individual alert controls what appears per row, using label names from the query result:
```
*ClusterName:* {k8s_cluster} | Node: {k8s_node_name} | CPU: {value}%
```

---

### Step 2 — Create an Alert Destination

A destination is the webhook or email endpoint that receives notifications. It must reference a template.

> ⚠️ A destination created **without a template** becomes a pipeline destination and **cannot be used with alert rules**.

**In the OpenObserve UI:**
1. Go to **⚙️ Management → Notification Destinations → New Destination**
2. Name it (e.g. `k8s_alert`)
3. Set type to `HTTP`
4. Enter your webhook URL
5. Select the template from Step 1
6. Set method to `POST`

**Via API (Slack example):**
```bash
curl -X POST \
  "https://<your-openobserve>/api/default/alerts/destinations" \
  -H "Authorization: Basic <base64(user:password)>" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "k8s_alert",
    "type": "http",
    "url": "https://hooks.slack.com/services/YOUR/SLACK/WEBHOOK",
    "method": "post",
    "template": "k8s_alert_template",
    "headers": { "Content-Type": "application/json" },
    "skip_tls_verify": false
  }'
```

**For email destinations:**
```bash
curl -X POST \
  "https://<your-openobserve>/api/default/alerts/destinations" \
  -H "Authorization: Basic <base64(user:password)>" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "k8s_email",
    "type": "email",
    "emails": ["oncall@yourcompany.com"],
    "template": "k8s_alert_template"
  }'
```

**Supported destination types:**

| Type | Use case |
|------|---------|
| `http` | Slack, PagerDuty, Microsoft Teams, any webhook |
| `email` | Email via SMTP |

### Step 3 — Import Alert Rules

Every file under `packs/<pack>/alerts/<category>/` is an alert definition
importable directly into OpenObserve. Imported packs deliberately ship
**without** a `destinations` field — a destination name from the library's
authors would not exist in your organization — so add yours before posting:

```bash
jq '. + {org_id: "default", destinations: ["my_slack"]}' \
  packs/databases/alerts/postgresql/postgresql_down.json |
curl -X POST \
  "https://<your-openobserve>/api/v2/default/alerts?folder=<folder_id>" \
  -H "Authorization: Basic <base64(user:password)>" \
  -H "Content-Type: application/json" \
  --data-binary @-
```

Or via the UI: **Alerts → Import → Add Alert**.

The `destinations` step is not optional: OpenObserve rejects an alert with an
empty destination list (`AlertDestinationMissing`), so importing a file as-is
through the UI will fail until you set one.

Library-only fields (`title`, `severity`, `docs_url`, `source`, `notes`) are
ignored by the API — `severity` in particular has no counterpart on the alert
resource and is not carried into the org. `tags` is the exception: OpenObserve
stores it as the alert's selection tags — so an imported alert arrives filterable by its
technology (`postgresql`) and its origin (`awesome-prometheus-alerts`).

`trigger_condition` units, since they are not uniform: `period` and `silence`
are **minutes**, `frequency` is **minutes** on the v2 API (which multiplies it
by 60 for the scheduler), and `tolerance_in_secs` is seconds.

Two things are worth reviewing before rolling an imported alert out widely:

* **Thresholds are the upstream author's, not yours.** They are starting
  points — `trigger_condition.period` and `promql_condition.value` are the two
  to tune.
* **The metric must already exist in your streams.** OpenObserve looks up the
  schema for `stream_name` when the alert is saved and refuses it with
  `StreamNotFound` if that stream has never been ingested — so an alert for an
  exporter you do not run cannot be installed at all, rather than installing
  and staying quiet. Install the packs for what you actually scrape.

## Contributing

1. Add alerts at `packs/<pack>/alerts/<category>/<name>.json` — that depth
   exactly. The filename must equal the `name` field inside.
2. Include `title`, `severity` (`critical` / `warning` / `info`) and a
   `description`. They are what the gallery draws, and they are required.
3. Strip instance fields — `id`, `org_id`, `destinations`, `owner`,
   `last_edited_by`, `last_triggered_at`, `last_satisfied_at`, `updated_at`.
   A raw export from a running organization is rejected.
4. Run `python3 scripts/validate_alerts.py` before opening a PR. Do **not**
   run or edit `scripts/generate_manifest.py`'s output: `manifest.json` and the
   pack table above are built by CI on merge.
5. Verify the query returns real data before committing.

The imported packs are the exception: they are regenerated wholesale from
upstream by `scripts/import_awesome_prometheus_alerts.py`, so a hand edit there
is lost on the next refresh. Send those fixes upstream.
